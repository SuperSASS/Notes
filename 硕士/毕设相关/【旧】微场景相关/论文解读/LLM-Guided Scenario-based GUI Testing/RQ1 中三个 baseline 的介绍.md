
# 三个基线方法的客观介绍

## 1. GPTDroid

### 基本信息
- **发表时间**: 2023年10月(arXiv), 2024年(ICSE 2024)
- **作者团队**: 南京大学(Zhe Liu等)
- **论文标题**: "Make LLM a Testing Expert: Bringing Human-like Interaction to Mobile GUI Testing via Functionality-aware Decisions"

### 核心思想
GPTDroid将移动GUI测试问题**形式化为问答(Q&A)任务**,让LLM通过"与应用对话"的方式进行测试。

### 方法概述

**基本流程**:
```
1. 将GUI页面信息传递给LLM
2. LLM生成测试脚本
3. 执行测试脚本
4. 将应用反馈传回LLM
5. 迭代整个过程
```

**核心创新**:
1. **功能感知的记忆提示机制(Functionality-aware Memory Prompting)**
   - 使LLM能够保留整个测试过程的测试知识
   - 进行长期的、基于功能的推理来指导探索

2. **基于文本的GUI表示**
   - 将GUI视图层次结构转换为文本
   - 发送给GPT模型请求下一步动作

### 技术特点

**LLM使用**:
- 使用GPT-3.5和GPT-4
- 基于文本提示技术
- 通过对话式交互理解应用功能

**测试策略**:
- 动作选择基于当前UI状态
- 利用历史测试轨迹积累知识
- 功能导向的探索策略

### 实验表现

**在93个Google Play应用上评估**:
- Activity覆盖率:比最佳基线高32%
- 缺陷检测:比基线多检测31%的bugs
- 发现了53个新bugs,其中35个被确认和修复

### 优势
- 开创了LLM在移动测试中的Q&A范式
- 功能感知的推理能力
- 能够进行类人交互

### 局限性
- 主要依赖文本表示,视觉信息利用不足
- 在ScenGen的对比中,成功率为68.69%
- 可能在复杂GUI理解上存在挑战

## 2. ScenTest

### 基本信息
- **发表时间**: 2024年6月(arXiv), IEEE TSE 2024
- **作者团队**: 南京大学(Shengcheng Yu等,与ScenGen同一团队的早期工作)
- **论文标题**: "Practical, Automated Scenario-based Mobile App Testing"

### 核心思想
ScenTest是**第一个实现完全自动化场景测试的方法**,通过**事件知识图谱(Event Knowledge Graph, EKG)**整合领域知识。

### 方法概述

**三大核心组件**:

1. **众包测试报告分析**
   - 从众包测试报告中提取测试事件和GUI信息
   - 识别4种实体和5种关系

2. **事件知识图谱(EKG)构建**
   - 为特定场景构建结构化知识图谱
   - 组织测试相关的领域知识
   - 实体类型:GUI控件、操作、场景、状态
   - 关系类型:触发、包含、前置条件等

3. **EKG引导的测试生成**
   - 结合应用当前状态和测试上下文
   - 采用深度优先策略
   - 记录触发不同子场景的事件

### 技术特点

**知识来源**:
- 众包测试报告
- GUI图像理解
- 专家经验编码

**测试策略**:
- 深度优先探索
- 子场景分支管理
- 状态初始化和回溯

**GUI理解**:
- 基于图像理解识别控件
- 控件关系建模
- 操作-控件映射

### 实验表现

**在124个应用、8个场景上评估**:
- 有效构建事件知识图谱
- 场景测试准确且充分
- 发现150+个真实bugs
- 在ScenGen的对比中,成功率为69.70%

### 优势
- 首个完全自动化的场景测试方法
- 系统性整合人类测试经验
- 知识图谱支持跨应用泛化
- 结合了GUI理解和领域知识

### 局限性
- 依赖预定义规则和知识图谱
- 构建EKG需要大量众包数据
- 对新场景的适应性有限
- 缺乏动态推理能力

> ## ScenTest中Scenario-based的体现
>
> **总结：与 ScenGen 一样，场景都是作为一个高层次的、声明式的测试目标描述（如登录 Login）**
> 
> ### 一、场景作为核心组织单元
> 
> #### 1. 测试场景的定义和选择
> 
> 根据论文信息,ScenTest在**8个最广泛使用的测试场景**上进行评估:
> 
> ```
> 典型场景示例(与ScenGen论文表1类似):
> - Login (登录)
> - Registration (注册)
> - Search (搜索)
> - Shopping Cart (购物车)
> - Note Taking (笔记记录)
> - Email (邮件)
> - Media Playback (媒体播放)
> - Social Sharing (社交分享)
> 等等
> ```
> 
> **关键点**:测试不是随机探索,而是**针对特定功能场景**进行。
> 
> ---
> 
> ### 二、事件知识图谱(EKG)的场景化构建
> 
> #### 核心机制:每个场景都有独立的EKG
> 
> ScenTest的独特之处在于:**为每个测试场景构建专门的事件知识图谱**
> 
> ```
> 场景1: Login
>   └─ EKG_Login
>      ├─ 实体:用户名输入框、密码输入框、登录按钮、错误提示...
>      ├─ 事件:输入用户名、输入密码、点击登录、验证失败...
>      └─ 关系:输入用户名 → 输入密码 → 点击登录
> 
> 场景2: Shopping Cart
>   └─ EKG_ShoppingCart
>      ├─ 实体:商品列表、加入购物车按钮、数量选择器...
>      ├─ 事件:浏览商品、选择数量、加入购物车、结算...
>      └─ 关系:选择商品 → 加入购物车 → 查看购物车 → 结算
> ```
> 
> **论文原文提到**:
> > "ScenTest extracts four kinds of entities and five kinds of corresponding relationships from crowdsourced test reports, where > the test events and app GUI information are presented, and **constructs the EKGs for specific scenarios**."
> 
> ---
> 
> ### 三、从众包报告提取场景知识
> 
> #### 场景知识的来源
> 
> ScenTest从众包测试报告中提取**与特定场景相关**的知识:
> 
> **提取过程**:
> ```
> 众包测试报告
>     ↓
> [过滤:只保留目标场景相关的报告]
>     ↓
> 提取4种实体:
>   1. GUI控件(Widgets): 与该场景相关的UI元素
>   2. 操作(Actions): 该场景中的典型用户操作
>   3. 状态(States): 场景执行过程中的应用状态
>   4. 场景步骤(Scenario Steps): 场景的关键里程碑
>     ↓
> 提取5种关系:
>   1. 触发关系(Trigger): 操作触发状态变化
>   2. 包含关系(Contain): 场景包含哪些步骤
>   3. 前置关系(Precondition): 步骤之间的依赖
>   4. 替代关系(Alternative): 同一目标的不同路径
>   5. 关联关系(Associate): GUI控件与操作的关联
>     ↓
> 构建场景特定的EKG
> ```
> 
> **示例:Login场景的EKG构建**
> 
> ```
> 从报告中识别Login相关内容:
> "用户打开应用,看到登录页面,
> 输入邮箱test@example.com,
> 输入密码,
> 点击登录按钮,
> 系统验证后进入主页"
> 
> ↓ 提取实体和关系
> 
> 实体:
> - 控件: [邮箱输入框, 密码输入框, 登录按钮]
> - 操作: [打开应用, 输入邮箱, 输入密码, 点击登录]
> - 状态: [登录页面, 验证中, 主页]
> 
> 关系:
> - 打开应用 → [触发] → 登录页面
> - 输入邮箱 → [关联] → 邮箱输入框
> - 输入密码 → [前置] → 点击登录
> - 点击登录 → [触发] → 主页
> ```
> 
> ---
> 
> ### 四、场景引导的测试生成
> 
> #### EKG如何指导场景测试
> 
> ScenTest在测试执行时,**始终以完成目标场景为导向**:
> 
> **测试生成流程**:
> ```
> 输入: 目标场景(如"Login") + 被测应用
> 
> 1. 加载Login场景的EKG_Login
> 
> 2. 确定场景目标:
>    目标 = "成功登录并进入主页"
> 
> 3. EKG引导的探索:
>    当前状态: 应用启动页
>    ↓
>    查询EKG: "从启动页到登录页需要什么操作?"
>    EKG返回: [点击登录入口]
>    ↓
>    执行操作 → 到达登录页
>    ↓
>    查询EKG: "在登录页完成登录需要哪些步骤?"
>    EKG返回: [输入邮箱 → 输入密码 → 点击登录按钮]
>    ↓
>    按序执行 → 验证是否达到场景目标
>    ↓
>    场景完成!
> 
> 4. 如果遇到分支:
>    EKG识别子场景(如"忘记密码"流程)
>    记录分支点,完成当前路径后回溯探索子场景
> ```
> 
> **论文原文**:
> > "ScenTest conducts test generation for **specific scenarios** on different apps with the guidance of EKG with the combination > consideration of app current state and testing context."
> 
> ---
> 
> ### 五、场景的跨应用泛化
> 
> #### 同一场景,不同应用
> 
> ScenTest的一个关键创新是:**同一场景的EKG可以用于不同应用**
> 
> **示例**:
> 
> ```
> Login场景的EKG (通用知识)
>     ↓
> 应用到不同App:
> 
> App A (社交应用):
>   登录入口: 底部Tab栏的"我的"
>   输入控件: 手机号 + 验证码
>   
> App B (购物应用):
>   登录入口: 首页右上角"登录"按钮
>   输入控件: 邮箱 + 密码
>   
> App C (工具应用):
>   登录入口: 启动后自动显示登录页
>   输入控件: 用户名 + 密码 + 记住我选项
> 
> ScenTest通过EKG的抽象知识 + 
> 当前应用的具体GUI状态结合,
> 自动适配不同应用的登录实现方式
> ```
> 
> **论文原文**:
> > "Then, ScenTest conducts test generation for **specific scenarios on different apps** with the guidance of EKG"
> 
> 这体现了**场景层面的泛化能力**,而不是应用特定的测试。
> 
> ---
> 
> ### 六、场景完整性保证
> 
> #### 深度优先的场景覆盖策略
> 
> ScenTest采用**场景完整性优先**的策略:
> 
> ```
> 主场景: 在线购物
> ├─ 主路径: 浏览 → 加购 → 结算 → 支付
> │
> ├─ 子场景1: 修改购物车
> │  └─ [记录分支点] → 完成主路径后回来探索
> │
> ├─ 子场景2: 使用优惠券
> │  └─ [记录分支点] → 完成主路径后回来探索
> │
> └─ 子场景3: 选择配送方式
>    └─ [记录分支点] → 完成主路径后回来探索
> 
> 执行顺序:
> 1. 完整执行主路径一次
> 2. 回到分支点1,探索"修改购物车"子场景
> 3. 初始化状态,回到分支点2,探索"使用优惠券"
> 4. 依此类推...
> 
> 确保每个子场景都被完整测试!
> ```
> 
> **论文原文**:
> > "ScenTest adopts a depth-first strategy. For each test event that may trigger different sub-scenarios, ScenTest can record > such an event. When one sub-scenario is complete, the app state will be initialized to the state of the recorded event to start > another sub-scenario, **until all the sub-scenarios are complete**."
> 
> 这确保了**场景级别的测试完整性**。
> 
> ---
> 
> ### 七、场景特定的验证
> 
> #### 基于场景的成功判定
> 
> ScenTest不仅执行操作,还要**验证场景目标是否达成**:
> 
> ```
> 场景: User Registration (用户注册)
> 
> 场景目标定义:
> - 成功创建账户
> - 收到验证邮件/短信
> - 能够使用新账户登录
> 
> 验证点:
> 1. 表单提交后,是否出现"注册成功"提示?
> 2. 是否跳转到验证页面?
> 3. 是否能在数据库中找到新用户记录?
> 4. 使用新账户登录是否成功?
> 
> 只有所有验证点通过,才认为"注册场景"测试成功!
> ```
> 
> 这与传统的"覆盖率"指标不同,ScenTest关注的是**场景的业务目标是否达成**。
> 
> ---
> 
> ### 八、与非场景方法的对比
> 
> 为了更清楚地理解ScenTest的"Scenario-based"特性,让我们对比一下:
> 
> #### 传统随机测试(如Monkey)
> ```
> 没有场景概念:
> - 随机点击任意控件
> - 无目标导向
> - 不关心业务逻辑
> ```
> 
> #### 传统覆盖率测试(如Stoat)
> ```
> 以代码覆盖为目标:
> - 尽可能覆盖更多代码路径
> - 不区分场景
> - 可能测试了很多无关功能,但核心场景不完整
> ```
> 
> #### ScenTest
> ```
> 场景为中心:
> - 明确场景目标:"完成登录"
> - EKG提供场景知识
> - 探索直到场景完成
> - 验证场景业务目标
> ```

## 3. ASOT (Automated Soap Opera Testing)

### 基本信息
- **发表时间**: 2024年12月(arXiv), FSE 2025
- **作者团队**: 新加坡国立大学、清华大学(Yanqi Su等)
- **论文标题**: "Automated Soap Opera Testing Directed by LLMs and Scenario Knowledge: Feasibility, Challenges, and Road Ahead"
- **注**:ScenGen论文中使用"ASOT"作为非官方简称

### 核心思想
ASOT探索**自动化探索性测试(Exploratory Testing, ET)**的可行性,也称为**"肥皂剧测试(Soap Opera Testing)"**。

### 背景概念

**探索性测试(ET)**:
- 利用测试人员的知识、创造力和经验
- 从最终用户视角创建变化测试
- 发现意外bugs
- 传统上依赖人工执行

**肥皂剧测试(Soap Opera Testing)**:
- 设计复杂测试场景来激发失败
- 模拟真实用户的复杂操作序列
- 像电视肥皂剧一样有连续情节

### 方法概述

**多代理系统架构**:

```
输入:肥皂剧测试(操作步骤列表) + 初始GUI状态

三个多模态代理协作:
├─ Planner(规划者)
│  └─ 将测试描述转为可执行计划
│  └─ 处理缺失步骤和过时描述
│  └─ 利用SKG的步骤知识
│
├─ Player(执行者)
│  └─ 执行规划的操作
│  └─ 定位GUI元素
│  └─ 处理替代执行路径
│
└─ Detector(检测者)
   └─ 实时bug检测
   └─ 页面内和页面间bug识别
   └─ 对比预期与实际行为
```

**场景知识图谱(SKG)**:
- 从bug报告构建
- 建模用户任务、失败和系统交互
- 支持替代执行路径
- 成本效益高(每个应用约$2-9)

### 技术特点

**多模态理解**:
- 结合自然语言和视觉理解
- 理解UI指令和UI变化
- 检测页面内和页面间bugs

**RAG增强**:
- 基于知识图谱的检索增强生成
- 利用众包知识
- 动态适应GUI变化

**Bug检测分类**:
- **页面内bugs**:单个UI内识别(如控件重叠)
- **页面间bugs**:跨多个UI页面观察(如状态丢失)

### 实验表现

**在3个应用、各10个肥皂剧测试上评估**:
- 提交34个bug报告
  - 3个已修复
  - 13个已确认
  - 6个分配优先级和严重性
  - 1个标记为重复
- 在ScenGen的对比中,成功率为73.74%

### 发现的挑战

**高误报率的四大原因**:
1. LLM幻觉(hallucinations)
2. 基于截图的GUI表示局限性
3. GUI元素定位不准确
4. 不合理或不必要的增强建议

### 优势
- 探索创新性测试范式
- 自适应场景图建模
- 多代理协作机制
- 结合神经和符号方法
- 真实bug发现能力

### 局限性
- 与人工执行仍有显著差距
- 场景边界探索不足
- 误报率较高
- 需要大量bug报告构建SKG
- 在处理意外GUI转换时灵活性有限

## 三者对比总结

| 维度 | GPTDroid | ScenTest | ASOT |
|------|----------|----------|------|
| **核心技术** | LLM问答 | 知识图谱 | 多代理+SKG |
| **知识来源** | 对话历史 | 众包报告 | Bug报告 |
| **GUI理解** | 文本表示 | 图像理解 | 多模态LLM |
| **测试策略** | 功能感知 | 深度优先 | 探索性 |
| **成功率(RQ1)** | 68.69% | 69.70% | 73.74% |
| **主要优势** | 类人交互 | 系统性知识 | 自适应探索 |
| **主要局限** | 视觉信息不足 | 规则依赖 | 误报率高 |

### 技术演进脉络

```
2023: GPTDroid
      └─ 开创LLM+GUI测试范式
      └─ 基于文本的Q&A方法
           ↓
2024: ScenTest
      └─ 引入知识图谱
      └─ 场景自动化
      └─ GUI图像理解
           ↓
2024: ASOT
      └─ 探索性测试自动化
      └─ 多代理协作
      └─ 场景知识图谱
           ↓
2025: ScenGen
      └─ 多模态LLM推理
      └─ 五代理精细协作
      └─ 上下文记忆系统
```

## 总结

这三个方法代表了基于场景的移动GUI测试领域的重要进展:

1. **GPTDroid**开创了LLM在GUI测试中的应用,证明了对话式测试的可行性

2. **ScenTest**首次实现完全自动化的场景测试,通过知识图谱系统化人类经验

3. **ASOT**探索探索性测试的自动化,通过多代理协作实现复杂测试场景

每个方法都有其独特贡献和适用场景,它们共同推动了该领域向更智能、更自动化的方向发展,为ScenGen等后续工作奠定了基础。
